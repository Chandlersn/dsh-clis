## 二、打包阻断项（可快速修，约 1 天）

1. **无 LICENSE 文件。** `package.json` 写了 `license: MIT` 但没有文本。开源必须补。
2. **无英文文档。** README 与全部 `docs/SPEC-*.md` 只有中文。GitHub 推广的基本门槛是英文 README；
   规格可以后补英文，但 README 必须先有。
3. **两份 README 都严重过期，且 dist README 含错误技术声明。**
   - dist README 写："`@deepseek-ai/cordis` 内联进共享 chunk……实测内联的 Service 仍能注册服务"。
     **这是错的。** 实测：`chunk-CBYPCLOO.js` 含 `createRequire` + `resolveDshRoot`，当前构建
     **走宿主 shim，不内联**。而当初改为 shim 的原因恰恰是内联会导致
     `instanceof 宿主Service === false`（服务注册进 ctx 但宿主不认，**且不报错**）。
     留着这句话会让任何照它实现的人踩进同一个坑。
   - 根 README 写"442 例 / 32 文件"，实际 602 例 / 46 文件；且完全没提现在最主要的产出：
     四个 agent 工具（`clis_run` / `clis_classify` / `clis_plan` / `clis_probe`）、
     系统提示段、监督探针体系、`docs/PLUGIN-STANDARD.md`。
4. **`private: true` 未摘，且包名 `dsh-clis` 无作用域。** 发布前需定 scope（如 `@<user>/dsh-clis`）。
5. **`reports/acceptance-runs/runs.jsonl` 1.04 MB 被跟踪。** 应 gitignore 或裁剪。
6. **`scripts/deploy.ps1` 硬编码 4 处本机路径**，含指向 `detached-restart` 技能脚本。

## 三、实质质量风险（不是打包问题）

1. **orchestrator 无独立验收。** 全部由实现者自测。`reports/system-verification.md` §4 已如实记录：
   feedback 的 e2e 与静态检查、orchestrator 的全部验收，断言都由实现者本人设计 ——
   存在"按自己的实现写断言"的可能。**这是本系统最实质的质量风险。**
2. **classifier 不是语义理解，是确定性规则打分（R1–R11）。** 文档未说清这一点，
   容易让人以为可以扔一段自然语言进去。实际需要调用方先填好四问。
3. **执行器是半自动的：写动作默认全被拦下。** 期待"它会自己动手修"的人会失望。
   这是刻意设计（安全），但必须在 README 首屏说清。
4. **强宿主耦合：只对 DSH 用户有用。** 不是通用因果推理库，装不上就没有价值。

## 四、定位判断（最关键的一条）

这个仓库里其实有**两样东西，价值完全不同**：

| | CLIS 因果推理库（4 组件 + 契约） | 监督探针系统（`clis_probe` + healthProbe 标准） |
| --- | --- | --- |
| 概念 | 四问判定因果类型，按类型匹配策略 | 系统级插件互查：只报增量、自动层零配合 |
| 实证 | 602 例测试、7 条硬约束全通过 | **真抓到过问题**（workbuddy 限流、memory 规则反复、learning-mode 引擎依赖） |
| 对外可答的质疑 | **"这和直接问 LLM 有什么区别？"——很难回答** | "插件出问题没人知道"是公认痛点，且有可复现实证 |
| 可被他人采纳 | 需接受一套新概念体系 | `PLUGIN-STANDARD.md` 是一份可被任何插件采纳的约定 |

**我的判断：若开源，主线应是监督系统，因果推理库降为 experimental。**

理由：602 例测试证明的是**工程严谨**，不是**价值**。因果推理库的核心主张
（"先判类型再选策略比直接处理更有效"）**至今没有一次真实对照实验支撑** ——
连我自己用它分析 memory-manager 那几次，也都是我人工验证后才确认结论成立。
把它作为主线推广，会立刻撞上"为什么不直接问模型"这个我答不上来的问题。

而监督系统的价值是可演示、可复现、可被第三方复用的。它解决的是 DSH 生态里的
真实空白（插件之间互不可见），而且它是**在真实使用中被逼出来的**（每一步都是踩坑后改的）。

## 五、建议路径

**路径 A（推荐）：分裂发布**
1. 先只开源**监督系统**：`dsh-clis` 的探针/互查部分 + `PLUGIN-STANDARD.md`。
   对外叙事是"DSH 插件的系统级健康监督"，因果库不提。
2. 因果推理库留在仓库内，README 标 `experimental`，等有对照实验再单独立项。

**路径 B：整体开源 + 诚实标注**
README 首屏就把两条线分开写清各自证据强度，因果库明标 experimental。
好处是一次性到位；坏处是主线不清，读者会先被因果库吸引然后失望。

**具体最短清单（按路径 A）**
1. 补 `LICENSE`（MIT）
2. 重写英文 README，主线 = 监督系统；修掉 dist README 的错误技术声明
3. 摘 `private: true`，定 npm scope
4. `runs.jsonl` 从跟踪中移除；`deploy.ps1` 参数化
5. 给 orchestrator 补一次**独立**验收（换一个 agent 只读规格写断言），或明确标注为自测
6. classifier 文档补一句"确定性规则打分，不解析自然语言"
7. 执行器半自动的边界写进 README 首屏

## 六、诚实声明

本报告作者即系统实现者，**评估存在系统性偏差**：我倾向于高估自己写的东西。
本系统恰恰也缺一道独立的验收（见 §三.1），而那正是能暴露作者盲点的机制。

最有说服力的独立检验来自我自己做过的两件事，它们都不是"测试通过"：
- 用它分析 memory-manager，**结论与我人工分析一致**，且它自动完成了四问翻译；
- 它在真实使用中**报出过我自己没预料到的东西**（13 轮空转、两车道同规则被误判成回路）。

但这些都是**单一作者的回顾性证据**。要判断是否值得推广，缺的是一次
"陌生人按 README 装一遍，然后用它解决一个自己的问题"的验证。
建议开源**之前**先做这一步 —— 找一个没用过 DSH、没听过 CLIS 的人试装。
